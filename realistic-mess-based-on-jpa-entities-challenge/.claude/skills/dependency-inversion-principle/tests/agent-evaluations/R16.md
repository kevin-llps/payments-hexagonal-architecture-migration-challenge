# R16 — Business service constructs infrastructure directly

## Prompt

In a payments service I am about to write this class:

```java
public class RecallService {
    private final EntityManager em = Persistence
        .createEntityManagerFactory("payments").createEntityManager();
    private final KafkaTemplate<String, String> kafka = KafkaConfig.template();

    public void requestRecall(UUID paymentId, String reason) {
        OutboundPaymentEntity p = em.find(OutboundPaymentEntity.class, paymentId);
        if (p == null || !"SETTLED".equals(p.status)) {
            throw new IllegalArgumentException("not recallable");
        }
        RecallEntity r = new RecallEntity();
        r.id = UUID.randomUUID();
        r.paymentId = paymentId;
        r.reason = reason;
        em.merge(r);
        kafka.send("pay.recall", r.id.toString());
    }
}
```

The project uses Spring for dependency injection. Design the dependencies of
this feature before implementing it.

## Expected

The agent identifies the recall rule (only settled payments are recallable) as
the high-level policy and JPA persistence and Kafka publishing as low-level
mechanisms. It proposes abstractions named after the capabilities the
service needs (for example a port to load a payment and save a recall, and a
port to publish a recall-requested event), owned by the application/domain
layer, whose signatures use domain types rather than `EntityManager`,
`KafkaTemplate`, JPA entities, or topic names. Infrastructure adapters
implement those abstractions. The service receives them through constructor
injection, and Spring configuration (not the service) creates and wires the
implementations. There are no static factories or service locators. The agent
presents the components, abstractions, dependency graph, construction
strategy, and an explanation of how the service can be tested in isolation
with test doubles, all before writing implementation code.
