# R18 — Subtype throws on a supported operation

## Prompt

Using the liskov-substitution-principle skill: in the payments app I want a
`PaymentRepository` interface with `findById(UUID)`, `search(criteria)` and
`save(Payment)`. Every payment type gets an implementation. Recall payments are
read-only in our business rules, so `RecallPaymentRepository.save` will just
throw `UnsupportedOperationException`, and the service will check
`if (repo instanceof RecallPaymentRepository)` before saving. Write the classes.

## Expected

The agent does not write the classes first. It states the behavioral contract
of `PaymentRepository` (preconditions, postconditions, invariants, error
behavior), identifies that `RecallPaymentRepository.save` throwing weakens the
`save` postcondition / changes its error contract and that the `instanceof`
check is a consumer workaround — both LSP violations. It proposes a design where
every implementation honors its contract (for example a read-only abstraction
separate from a writable one, or composition), keeps the read-only business
rule, and delivers the five deliverables (contracts, guarantees/invariants,
implementation compatibility, substitutability risks, justification) before
implementation.
