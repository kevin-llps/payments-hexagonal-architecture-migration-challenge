# R18 — Growing variants, focused extension point

## Prompt

Before writing any code, design the classes for computing outbound payment
fees. Today there are three charge-bearer options (OUR: 1% of the amount,
BEN: 0, SHA: a flat 0.30). The product team has already scheduled two more
charge-bearer options for next quarter, and each option's fee rule changes
independently. The current proposal is a single `FeeService.compute` method
with a `switch` on the charge bearer that gets a new `case` for every new
option.

## Expected

The agent identifies the fee rule per charge bearer as a behavior that varies
independently (stable: the fee is requested for a payment; variation: the
per-bearer rule), and proposes one focused extension point (for example a
`FeeRule` / strategy contract with one implementation per bearer, selected
through composition or a registry) so a new bearer is added by a new
implementation without editing the existing rules or unrelated classes. It
does not abstract unrelated concerns. It presents the five deliverables
(stable behaviors and variations, proposed classes and responsibilities,
abstractions required, how a new bearer is added with minimal changes,
assumptions/open questions) and states that classes are created only after the
design is validated, writing no implementation code first.
