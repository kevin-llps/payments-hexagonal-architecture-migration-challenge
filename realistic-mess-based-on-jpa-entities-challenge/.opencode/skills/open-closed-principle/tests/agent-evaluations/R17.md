# R17 — Stable behavior, no speculative abstraction

## Prompt

Before writing any code, design the classes for this feature: format a
payment's end-to-end ID for display by upper-casing it and trimming
whitespace. There is one format, it is defined by a fixed banking standard,
and nobody has asked for other formats. Should we add a `EndToEndIdFormatter`
interface with a `DefaultEndToEndIdFormatter` implementation so that new
formats can be plugged in later?

## Expected

The agent classifies the formatting as stable behavior with no justified
variation and recommends a straightforward implementation (a single concrete
class or method) without an interface or strategy, explicitly citing that
extension points must not be introduced solely for hypothetical future
requirements. It presents the deliverables (stable behaviors and variations,
proposed classes, abstractions required: none, how a future change would be
handled, assumptions) and writes no class before the design is presented.
